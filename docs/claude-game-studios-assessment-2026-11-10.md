## 1. 结论

**值得吸收，主要价值是游戏开发的工作流、角色库、产物模板和验证方法。** 它与此前两个插件形成互补：

| 来源 | 在工作台中的作用 | 主要复用对象 |
| --- | --- | --- |
| Claude Code Game Studios（本文简称 CCGS） | 组织“做什么、谁来做、按什么证据验收” | 简报、角色模板、开发阶段、玩法迭代、评审与测试证据 |
| dsh-game-studio | 创建和运行可玩原型 | 工程、构建、素材槽、快照、试玩、导出 |
| dsh-drawai | 制作和编辑设计 / 视觉产物 | 流程图、关卡关系、分镜、SVG / PNG、后续媒体能力 |
| dsh-workbench | 承载项目、调度和日常协作 | 项目、产品、任务、笔记、智能体、Bug、测试、资产引用 |

推荐吸收 CCGS 的轻量原型流程与证据结构，按需转化专业角色；不把整套仓库复制进工作台根目录，也不要求全部用户安装 Claude Code 才能使用游戏模块。

该项目本身是 Claude Code 项目模板。根目录没有可启动的工作台应用，`src/` 只有占位和说明；不过 `.claude/scripts/` 中确实有可执行辅助实现，不能将其概括成只有提示词。

本次只做本地评估与工作区文档更新。候选仓库里的 `CLAUDE.md`、技能正文和 settings 均按待分析资料读取；没有启用其规则、执行技能、启动子智能体或接受其中自动提交 / 安装指令。

## 3. 最值得借鉴的流程

### 3.1 一页简报先形成可验收范围

`prototype` 流程先收集少量关键选择，输出 `design/game-brief.md`，保留用户原话、风格、第一分钟、挑战、Keep / Avoid / Out of scope 和待实现内容，再进入构建。

工作台可将简报作为产品设计下的游戏文档模板，并给出编辑 / 确认入口。配置从模板解析后成为工作台的结构化字段，不依赖模型每次自行寻找 Markdown 标题。

### 3.2 机器检查与真人试玩分开记录

流程区分 built、missing、broken 与 not assessed，交付卡明确“尚未经真人试玩”。机器能证明加载、输入响应、状态和部分视觉问题，不能替代用户对趣味性和手感的判断。

建议游戏模块分别保存：构建结果、机器检查项、未评估项、人工试玩结论及来源版本。只有人工明确反馈后，才记录继续、转向或终止等产品决策。

### 3.3 改动保留范围、检查点和调参记录

CCGS 把用户要求保留 / 避免的内容带入每次修改，用检查点支持回退，调参数时记录目标与效果。工作台可结合 Game Studio 版本机制形成“改了什么 / 为什么 / 对比哪个版本 / 试玩结果”的记录。

CCGS 原流程使用 Git commit / tag；工作台首期可用已有游戏快照作为检查点。是否提交用户仓库由工作台现有授权流程决定，不照搬技能内自动提交步骤。

### 3.4 同种子、同输入的回放

`one-shot-driver.js` 和 `one-shot-run.sh` 固定时钟与随机输入，输出状态、场景、卡住、异常、输入和截图相关记录；升级 Web 工程时比较同种子回放。

这是有价值的回归方法，但项目的完整契约主要是 `window.game.step()`、状态 / 事件与输入控制，Game Studio 使用 `window.__gameState()`、可选 `__autoplay()`。只知道当前状态不等于具备确定性步进，不能简单重命名接口就宣称精确回放。

建议报告标明 `deterministic-replay`、`state-autoplay`、`input-smoke` 或 `not-assessed` 等能力级别。提供完整步进适配时才启用精确回放；只能键盘烟测时显示实际范围。

### 3.5 流程强度可调

CCGS 默认 `minimal`，可升级为 `standard` / `full`，控制文档、QA、Story 粒度和评审人数。工作台可以提供轻量原型和正式项目两个起点，遇到网络、经济系统、上线等复杂任务时按需加强检查，不强迫每次小修改都走完整工作室流程。

## 4. 与工作台现有智能体系统的差距

### 4.1 角色库应按需选取

工作台 `src/host/agent-model.ts` 当前限制单队 12 人、最多 3 名运行成员，每个功能绑定最多 6 个候选执行人。49 个 CCGS 角色适合作为可选角色库，不应作为单个团队一次启动。

建议默认选 5 个职责：制作 / 主理人、玩法设计、玩法程序、美术 / 技术美术、QA；按引擎替换程序专员，数值、音频、叙事、网络、性能在需要时加入。此处为未来产品配置建议，本次未启动团队。

### 4.2 提示词不能直接贴入成员配置

工作台 `AGENT_LIMITS.prompt=4000`，`validateMember()` 会裁剪过长系统提示词。本次测得 **49 个 Agent 原文件全部超过 4000 字符**，最长约 1.87 万字符。

原样粘贴会丢失后半段，可能损失交付和约束。应抽取短角色卡，将长资料作为按需读取的版本化参考文件；或者另外实现显式文件引用。导入时必须提示长度和转换结果，不静默截断。

### 4.3 工具和模型声明需要转换

CCGS frontmatter 中的 `Agent`、`Read`、`Write`、`Bash`、`WebSearch`、`model: opus/sonnet/haiku/inherit`、`maxTurns`、`memory: project` 以及 skill 的 `allowed-tools`、动态 shell 注入都是其宿主语义。

工作台使用 DSH 服务、`spawn_teammate`、`team_task_*`、工具名、provider / model、技能和 MCP 配置。需要显式映射：不支持的声明显示降级，模型由工作台现有设置选择，工具授权由宿主实际执行，不能认为写进提示词就完成隔离。

角色库的静态文档引用不要求重启记忆库改造；本阶段可不迁移 CCGS 的 Agent memory 和 session-memory 机制。

### 4.4 游戏任务需要自己的派发与交付协议

工作台已有功能绑定列表不含游戏功能；当前 kickoff 专门处理灵感、UI 与 DEMO，其他功能可能落入灵感式交付分支。

未来应增加明确的游戏功能，例如简报、原型构建、玩法改动、素材、试玩和评审，并定义各自结果。不能把游戏任务仅命名为 `game.build` 后仍要求成员调用 `workbench_idea_expand`。可参考现有实现模式，但不把游戏 HTML 强行写成普通 UI DEMO。

## 5. 必须分离的工程与运行时

### 5.1 CCGS 默认一个仓库就是一个游戏

它把 `project.yaml`、`design/`、`production/`、`src/`、根 `package.json` 和 Git 标签当成单项目状态。工作台承载多个项目和多个游戏。

`one-shot-grow.sh` 的 guard 会拒绝已有根 `package.json` 或已有源文件等情况；copy / record 阶段会生成工程文件并更新 `project.yaml`、`CLAUDE.md`。在 `dsh-workbench` 根目录运行成长流程既不符合模板假设，也会碰到工作台自己的工程。

所有生成、升级与测试必须指向明确的游戏工程根。轻量 Game Studio 工程与 Vite 游戏工程需区分类型；后者不能沿用前者只认识 `game.json + game.js` 的构建器。

### 5.2 引擎专员与引擎接通是两回事

该项目确实有 Unity、Unreal、Godot 专员，以及 `test-run.sh` 中的 Unity batchmode Test Framework、Unreal Automation、Godot 等执行 / 结果解析分支。不能因为 `engines.tsv` 中 Unity / Unreal 默认命令是 `-` 就断言完全没有测试实现。

但这些实现依赖实际编辑器路径、包、项目、测试、平台和配置；README 也承认引擎路线缺少同等级实证。因此对工作台而言，它提供的是可移植的适配起点，尚不能当作已经可用的 Unity 编辑器桥接、场景修改、资源导入或端到端发布能力。

### 5.3 Bash Hook 不会自动作用于 DSH

CCGS settings 的 Hook 依赖 Claude Code 事件和环境变量，脚本依赖 Bash、AWK、Python，部分验证依赖 jq 与浏览器。当前 PowerShell 的 `Get-Command bash,sh` 未找到命令，两个常见 Git Bash 安装位置也未找到；这只说明本次探测环境，不代表系统其他位置不存在。

建议将首期需要的文件检查、配置解析和报告归一化实现为工作台宿主可调用的 Node / TypeScript 能力。若以后复用原脚本，先检测并配置明确的 Bash 路径、执行目录和子进程取消机制。

不能用“Hook 文件复制过来”代替 DSH 的权限与验证接入。原项目每次写文件前确认、阶段审批等交互也应按工作台已获授权的任务范围重新设计，避免把操作摩擦一起搬入。

## 6. 建议的最小吸收范围

### A：在原有游戏模块方案上增加流程层

1. 选取 `game-brief`、试玩交付卡、变更 / 调参记录、测试证据、简版发布检查表，做中文且可维护的工作台产物模板。
2. 提供 5 人左右的游戏团队预设与引擎专员选项；保留原始来源和转换版本。
3. 将流程串成“简报 → 构建 → 机器检查 → 人工试玩 → 修改 / 回退 → 导出”，由 Game Studio 核心执行可玩产物操作。
4. DrawAI 画布关联简报、玩法或素材，导出图片再进入游戏素材候选。
5. 报告分别记录通过、失败、未评估，所有证据关联工程、构建 / 版本、执行条件。

### B：后续扩展长期项目能力

用户确认长期维护后，再增加 Vite 游戏工程类型、确定性回放、Story / Sprint、数值 / 网络 / 叙事专组、引擎任务与测试适配。Unity 游戏项目仍使用实际 Unity 工程，不能以浏览器原型通过代替 Unity 项目通过。

整套 75 个主技能、49 个角色、全部 Hook、完整审批体系和自我改进测试框架不作为首期接入要求。

## 7. 实施顺序与验收

本建议在 `game-module-plugin-assessment-2026-11-10.md` 中单列 **P1.5：游戏开发流程层**，不向原 P0 / P1 追加交付项。P0 仍验证项目与宿主适配；P1 仍完成 Game Studio 的核心闭环。角色映射、简报、交付卡、流程状态及测试能力级别契约均计入 P1.5，单独估算、实施和验收；基础画布仍按 P2 推进。

P1 不以完成 P1.5 为验收条件。P1.5 依赖 P1 的工程标识、构建和版本结果；流程关闭时，P1 的创建、试玩和导出仍可独立使用。P1.5 完成基础证据记录，自动试玩报告与测试 / Bug 的完整联动仍属于原 P3。

| 阶段 | 产出 | 验收要点 |
| --- | --- | --- |
| P0 / P1（原方案） | 项目与宿主验证、Game Studio 核心 | 按原范围验证创建、导入、构建、试玩、素材、版本与导出；不要求 CCGS 流程层 |
| P1.5-A：流程契约 | 角色映射、团队预设、简报与交付字段、测试能力级别 | 过长提示词不静默截断；未支持工具 / 模型声明可见；产物绑定工程与版本 |
| P1.5-B：流程与证据 | 简报编辑、交付卡、机器结果摘要、真人反馈 | 没跑测试不显示通过；截图不替代玩法验收；未真人试玩明确标记；关闭流程不影响 P1 |
| P2（原方案） | DrawAI 与设计 / 素材关联 | 画布保存 / 导出可回溯到对应工程与槽位，不自动将图当成可执行玩法 |
| P3（原方案） | 自动试玩报告与测试 / Bug 联动 | 复用 P1.5 基础证据，完成测试与问题的双向关联 |
| 后续专项 | Vite / 引擎类型、确定性回放、Story | 每种工程独立构建器；精确回放能力真实验证；不写工作台源码根 |

P1.5-A / B 是该期内部拆分，不计为原 P0 / P1 的隐含工作。其估算需计入角色转换、界面、持久化、派发 / 交付适配和证据状态；未估算前不承诺与原 P1 共用工期。若需要更早交付基础画布，可调整 P1.5 与 P2 的执行顺序，但仍保留各自范围与验收。
