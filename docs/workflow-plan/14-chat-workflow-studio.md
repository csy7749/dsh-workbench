# 14 聊天工作室与节点工作流协同

状态：规划草案。混合方向已获用户认可；实现、宿主能力和增量工期待验证。依赖：01–04、08、09、13。

## 1. 产品定位

聊天负责探索、指挥和临时协作；工作流负责可重复交付、版本和审核。两者共用执行配置、执行器、任务、预算、事件和产物系统，用户可以在同一创作产品下切换入口。

交互方式与执行人数是两个维度：聊天可以单 Agent，节点也可以使用团队。多人角色名称不代表更高质量，只有明确分工、输入、工具和独立证据时才引入多个员工。

## 2. 优缺点与选择

| 维度 | 节点工作流 | 聊天工作室 |
| --- | --- | --- |
| 启动与探索 | 需要模板 / 契约，重复任务启动稳定 | 即时表达、追问和改方向，前期成本低 |
| 需求变化 | 固定步骤可能限制探索，变更需处理依赖 | 临时讨论灵活，但需定位影响范围 |
| 重复生产 | 明确步骤和采用门，容易复用 | 依赖主理人重复拆解与协调 |
| 上下文 | 版本明确、有界；未结构化背景可能遗漏 | 背景丰富；长会话易混入旧决定 |
| 恢复和审计 | 按节点、尝试和快照恢复 | 仅靠聊天难重建，需额外任务和产物记录 |
| 人工参与 | 审核点清晰，过多审核可能打断 | 随时插话，但指令范围易歧义 |
| 成本 | 平台前期建设高，稳定后可限制重跑 | 上手快，协调和重复讨论成本易波动 |
| 多 Agent | 依赖、产物和并发清楚 | 临时组织灵活，可能重复工作 / 文件冲突 |
| 质量 | 结构和证据可约束，不能保证内容优秀 | 讨论能深入，但共识不能代替验证 |

游戏玩法讨论、小说人物动机和短剧创意适合先聊；确认规则后的构建、按大纲生成章节、场次审校和导出适合工作流。新任务可先聊成简报，再转为固定流程。

## 3. 三个入口和共享结构

| 入口 | 用户用途 | 输出归属 |
| --- | --- | --- |
| 产品工作室聊天 | 探索、问答、委派、评审方案 | 产品级讨论任务和候选产物，不伪造工作流 Run |
| 工作流运行 | 按固定定义逐步交付 | WorkflowRun / Step / Attempt |
| 节点内协作聊天 | 在某个输出上解释、修订、组织评审 | 关联该 Step、基准快照和协作任务 |

建议共享操作上下文：`projectId / creativeProductId / operationId / optional runId / optional stepId / optional attemptId / sessionId / profileVersion / inputManifest`。

产品级讨论不具备 runId 时，仍有独立 operation / task 身份并复用产物、执行收据、预算和事件协议；不为每句聊天建立工作流。只有用户启动模板或节点任务时才创建相应 Run / Attempt。

## 4. 聊天进入工作流

```text
聊天探索 → 候选简报 / 设计 → 编辑与采用
  → 选择工作流版本 → 显式绑定已采用快照 → 创建运行
```

“保存为候选”只将选定内容登记成有来源产物；“启动工作流”需要选择类型、模板和输入映射。普通问答无需逐条存成正式快照；决定或交付物需显式提升，不能把模型总结当成用户已经批准的产品决定。

从聊天提炼的动态页面 / 网络材料保留来源，输入内容不能扩大执行权限。启动前展示上下文摘要和未确认项，避免把全部长会话无界塞入下一节点。

## 5. 工作流打开节点协作

1. 节点正在审核时，用户选择“协作修订”，冻结该次协作的基准 snapshotId / draftRevision、意见和可写范围。
2. 可由一个 Agent 执行；需要时按明确任务启用策划、程序或 QA，复用 13 的配置和原有团队适配。
3. 协作产出新候选和报告，不能直接替换当前 Draft / Adoption。
4. 用户比较和修改候选，采用时重新检查基准、验证报告和输入是否仍有效。
5. 采用后由工作流调度器决定继续和 stale 传播，聊天主理人不能仅凭一句“已完成”推进。

这里的节点审核发生在显式 `human.edit-confirm`：协作 Agent 只提交新候选，不能代替用户确认。自动节点没有人审时按机器校验 / 系统采用正常继续；用户查看或讨论它不额外插入隐藏审核。若讨论要改变正在运行的输入，先明确暂停 / 派生新运行；普通产品聊天候选的提升仍需用户操作，不冒充工作流的系统采用。

协作不自动触发 Step 的新执行。如果用户选择“重跑节点”，必须先处理原 Attempt 的取消 / 对账，再创建新 Attempt，避免聊天与队列同时生成两份被误认为当前的输出。

## 6. 聊天变更的影响处理

例：“把单人游戏改成双人合作”。系统先生成变更候选，列出受影响规则、工程、素材、测试和未知影响。讨论意见本身不立即失效现有下游；用户采用新规则后，按 02 标记真实依赖后继 stale。

如果变更要求改模板、权限、模型或新增节点，则创建定义 / 配置草稿并派生运行，不能借聊天热改正在执行的计划。实际代码修改在隔离工程工作副本进行，正式文件发布仍经审核和 outbox。

只替换同一定义下的已采用上游时按 02 暂停、对账、CAS 更新采用并传播 stale，再显式继续；更换创建运行时固定的外部资料或终态运行仍派生新 run。聊天入口不能使用比界面更宽松的版本变更规则。

无关闲聊不取消运行；明确的暂停 / 停止命令映射成结构化操作，并返回真实执行状态。作用范围有歧义时，先给出拟操作目标，未明确前不执行跨产品 / 多运行变更。

## 7. 多员工协作规则

- 主理人负责分解和汇总，员工收到稳定任务、输入版本、写范围、输出契约和预算。
- 默认单执行者；确有收益才启用实现 / 独立验证等多角色，不默认全员开会。
- 模型一致或多模型投票不能证明结论正确；评审要提交可核查证据与未评估项。
- 多员工共用总预算、并发配额和取消范围，各自会话 / 尝试可追溯；费用统计不重复累计主任务与子任务。
- 主理人不得把讨论共识升级为用户采用，也不能绕开硬校验和工具权限。
- 现有 DSH 团队隔离 / 并发能力不足时显示限制，先用顺序单员工交付；不新造第二套 Agent runtime。

## 8. 上下文、恢复和模型切换

聊天历史由 DSH 会话维护，工作台保存关联 ID、已采用决定、候选、任务和来源，不复制完整消息存储。跨模式交接使用显式快照和有界摘要；摘要也是带源版本的产物，源变更需重新检查。

模型切换按 13 创建新的执行身份和上下文清单，不假设不同模型共享隐含记忆。刷新 / 压缩 / 会话不可用后，从任务、快照和事件恢复事实；无法恢复的讨论不冒充已完成任务。

独立聊天不自动写入暂停中的个人 / 项目记忆库；需要保存的产品事实先作为正式产物采用。

## 9. 独立实施阶段 C

| 阶段 | 内容 | 平台依赖 | 不隐含包含 |
| --- | --- | --- | --- |
| C0 交接 Spike | 聊天保存候选、绑定输入、基准校验、权限 / 事件探测 | W1/W2、13 执行配置 | 不要求多员工或新聊天主界面 |
| C1 基础协同 | 单 Agent 聊天候选 → 工作流；节点内修订 → 采用 | C0、最小审核 UI | 不要求团队自动调度或运行中热改 |
| C2 多员工工作室 | 显式分工、团队预算、独立证据和节点团队适配 | C1、DSH 团队验证 | 不包含公开发布、模型投票平台 |
| C3 便利交互 | 从探索保存可复用模板、更多批量交接 | W3/W6 及真实需求 | 另行估算，不自动生成可执行脚本 |

这是新增工作包，独立估算和发布开关，不塞入原 W1/W2 或游戏 P1/P1.5 的既定工期。基础工作流无需等待 C2，现有聊天入口无需等工作流完工。

## 10. 任务和验收

- C0-01：结构化交接清单、基准与上下文协议，验证同产品绑定和不越权。
- C1-01：保存聊天选段为候选、编辑 / 采用、映射模板端口并创建运行。
- C1-02：节点协作修订入口，基准冲突、迟到回调和刷新恢复。
- C1-03：聊天变更预览、stale 影响列表和明确继续 / 暂停动作。
- C2-01：团队任务 / 子会话、权限、预算、并发和取消验证。
- C2-02：独立评审证据，不把主理人汇总或投票当作验收通过。
- C3-01：按真实需求整理可复用模板；批量交接依赖 W6，单独确定范围与验收。

必须验证：聊天候选未采用不推进；对话不能直接改正式产物；用户编辑过程中 Agent 回写不覆盖 Draft；上游采用后影响一致；产品级任务无 runId 也有来源；两种入口不重复发起同一执行；取消能说明子任务真实状态；更换模型、角色、Skill、MCP 的有效配置可核查。

## 11. 风险与回退

首要风险为两套状态、两次执行和聊天暗改正式文件。使用共用执行器和采用 / 发布服务、幂等操作、上下文身份及单独功能开关。停用 C 模块保留会话链接、候选与审计，工作流和原 DSH 聊天仍可独立使用。未完成子任务先对账，不通过关闭 UI 假定实际执行已停止。
