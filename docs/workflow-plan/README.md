# 多产品工作流平台 · 总目录

状态：规划草案 v0.5，尚未实施。日期：2026-11-10（Asia/Shanghai）。本版纳入 OhMyGame 三项机制，并按用户要求将人工编辑确认设为显式节点；没有人工节点的路径在机器校验通过后自动继续。ComfyUI 可选服务后端仍待排期和验证。

目标仓库：`D:/AI/dsh-workbench/`。本文是后续设计、估算、实现和验收的统一入口。

## 1. 产品目标

用户可以选用或配置一条工作流，自动运行节点并查看每一步的输出。需要用户编辑确认的位置插入 `human.edit-confirm` 节点，运行到这里等待用户保存并确认；没有该节点时，输出经必要机器校验和系统采用后自动进入下一步。系统保留原始输出、修改版本、输入来源与执行记录，支持暂停、恢复、重试和从历史版本继续。

长期支持软件产品、游戏、小说、短剧等不同创作对象。平台共享运行、产物版本、人工审核和任务呈现；领域规则、编辑器、验证器和执行能力由产品包提供。

同时保留聊天工作室与节点工作流：聊天用于探索、指挥和临时协作；工作流用于稳定交付、审核和恢复。两者共用模型 / 角色 / Skill / MCP 执行配置和产物体系，节点内也可按需组织多员工。聊天形成候选后，经采用才能成为正式流程输入。

这里的“产品”是创作对象，例如一款游戏、一部小说、一部短剧。工作区是文件和执行范围；一个工作区可以包含多个产品，一个产品可以拥有多条工作流和多次运行。现有软件产品数据模型不能直接强套到其他领域。

## 2. 成功标准

1. 同一内核支持“自动节点 → 人工编辑确认 → 自动节点”和不含人工节点的连续执行；等待与草稿刷新后可恢复。
2. 原始结果和历史确认版本不被编辑覆盖，任意下游结果能追溯到实际输入版本。
3. 上游变化后，受影响下游显示过期，不能静默把旧结果当成基于新输入的结果。
4. 失败、中断、取消、未评估和人工驳回具有明确语义，不以会话退出码代替产物验收。
5. 游戏、小说、短剧可以复用内核，而不是各复制一套运行系统。
6. 旧产品入口、用户文件与原有数据在迁移和停用新功能后仍可使用。
7. 聊天与工作流交接不重复执行、不绕过审核；请求和实际生效的模型 / 角色 / Skill / MCP 配置可追溯。

## 4. 设计基线

| 原则 | 约束 |
| --- | --- |
| 快照不可变、工作副本可改 | 修改生成新版本；确认记录和当前选用指针与快照内容分开 |
| 定义与运行分开 | 运行固定模板版本、产品包版本、配置和输入；编辑模板不改历史 |
| 人工确认显式成节点 | 只有 `human.edit-confirm` 等人工任务节点等待用户；普通节点校验后系统采用并自动继续，保存草稿不触发确认 |
| 自动采用与人审可区分 | Adoption 记录 system / human 来源；自动继续不省略机器校验，也不扩大付费或发布权限 |
| 产物有类型 | 不把游戏工程、小说章节、短剧场次都降成聊天文本 |
| 小内核、领域适配 | 不重做 DSH 模型 / 团队运行时；工作流只负责节点间编排与产物交付 |
| 可配置节点先落地 | 首期固定步骤列表、执行者、输入版本和显式人工节点，W3 开放配置 / 增删；自由画布后做 |
| 暂停记忆工作 | 引用静态资料即可运行，不恢复记忆库实验，不自动追加模型验收 |
| 分期不隐性叠加 | 通用平台 W 阶段与游戏 P 阶段分别计量，共用基础只计算一次 |
| 双入口共用内核 | 聊天和工作流共用执行 / 产物 / 审核；多 Agent 是执行方式，不是另一套后台 |
| 配置必须实际生效 | 模型路由、角色与 Skill 加载、工具开放有收据，提示词中的名称不算接通 |

## 5. 首个试点

将现有产品设计流水线转为工作流模板：

```text
选定并冻结产品导图
  → 生成模块设计文档 → 用户编辑确认
  → 提炼模块结构 → 用户编辑确认
  → 生成产品设计文档 → 用户编辑确认
  → 一致性检查报告 → 用户编辑确认 → 完成 / 修订后重跑
```

上图每个“用户编辑确认”都是独立 `human.edit-confirm` 节点；这是带人审的默认试点模板，不是平台对每个生成节点的隐式拦截。移除这些节点并发布新模板后，合法输出自动采用并继续；失败、过期或缺能力仍停止。现行事实来源规则保持：导图为软件产品设计事实基准；人工修改文档若与导图冲突，要修改事实来源或保留待确认冲突，不能通过审核按钮隐藏冲突。首期一致性节点只出报告，修复由显式新尝试执行。

选择这个试点，是因为仓库已具备相应文档、导图、派发和版本基础；是否可安全隔离现有直接写回工具，仍需 W0 Spike 验证。验证失败先以假执行器完成闭环，不宣称已经接通生产流水线。

## 6. 总体分期与依赖

| 平台阶段 | 交付 | 依赖 | 阶段出口 |
| --- | --- | --- | --- |
| W0 契约与技术验证 | 状态、快照、文件发布、DSH 完成契约验证 | 当前代码核对 | Spike 报告与决策通过 |
| W1 最小内核 | 持久运行、线性调度、快照、人工编辑确认节点、系统 / 人工采用、恢复；假执行器 | W0 | 无模型也能演示有 / 无人工节点、暂停 / 修改 / 继续 |
| W2 产品设计试点 | 四步适配、最小运行界面、已有笔记编辑 | W1 | 真实流水线可单步恢复，旧入口仍可用 |
| W3 节点配置与受限编排 | 参数 / 执行者 / 输入绑定，增删可选步骤，定义版本 | W2 | 配置校验、模板发布、运行固定版本 |
| W4 产品包与游戏流程 | 包注册、领域产物、游戏流程层；接可用游戏后端 | W2；游戏 P0/P1 独立通过 | 游戏可暂停迭代，关闭流程仍能独立操作 |
| W5 小说 / 短剧验证 | 最小小说包、短剧包、章节 / 场次版本 | W4 的包契约 | 两类新产品无需复制内核 |
| W6 高级编排 | DAG、分支比较、批量节点、可视化编排 | W3、W5 的实际需求 | 拓扑、资源和历史版本验收通过 |

W4 的游戏流程对应原评估 **P1.5**，单独估算。原 P1 是游戏核心；P2 是画布；P3 是自动试玩与测试 / Bug 联动；P4 是媒体与发布。详见 [里程碑映射](11-roadmap-backlog.md)。阶段编号代表交付边界，不代表可以跳过依赖。

新增执行配置任务 E 按 W0/W1/W2/W3 分别列增量；聊天协同 C0–C3 单独估算，C1 先做单 Agent 双向交接，C2 才接多员工。它们不是原 W 阶段或游戏 P1 的隐含工作，基础工作流不等待完整工作室上线。

素材工作流新增 S0–S4：S0 本地试验 → S1 静态素材桥 → S2 动画图集，S3 受控生成可在 S1 后独立排期，S4 视频 / 高级媒体与 P4 协调。S0 可先独立验证；S1 独立操作依赖 P1，正式流程另依赖 W1/W2 和 W4 包注册。各期单独估算与验收，基础 W / P 阶段不等待 sprite-gen；具体依赖以 [15 素材工作流](15-asset-workflow-sprite-gen.md) 为准。

ComfyUI 为后续可选后端，预留模板版本、参数映射、异步任务与产物捕获接口。它可直接产出素材或接 sprite-gen 后处理；接入候选任务 S3-C01–S3-C03 单列，具体部署与 API 待验证，不成为当前 S3 或工作流内核的必需依赖。

## 7. 首期明确不做

- 任意脚本节点、第三方节点市场、跨机器分布式调度。
- 任意循环、无限自动重试、自动分支合并和跨产品自动转换。
- 全量搬入 CCGS 49 个角色 / 75 个主技能及其 Hook。
- 强制迁移所有现有模块、重写现有数据库、恢复记忆库研发。
- 用视频渲染、Unity / Unreal 编辑器接通作为工作流内核验收前置。

## 8. 工程组织与维护

建议新增 `src/host/workflow/`、`src/shared/workflow/`、`src/client/workflow/` 与 `src/packs/`。实际路径在 W0 确定，不继续向大型 `index.ts` / `app.ts` 填入整套实现。内核、UI、产品包和宿主适配分开，避免领域提示词侵入调度器。

每个模块文档是该模块范围的唯一入口；实体和状态以 01 为准，快照以 02 为准，分期以 11 为准。更改跨模块契约时同时更新引用方和 12 的决策记录。

执行配置以 13 为准，聊天 / 节点交接以 14 为准。产品级讨论不强制创建 WorkflowRun，但正式候选、任务和调用均需稳定来源，不能依赖聊天记录中的一句“完成”。

素材工具适配和产物消费以 15 为准；任务统一在 11 维护，验收统一在 10 维护。sprite-gen 作为可选执行后端，复用产物 / 审核 / 执行服务，不复制工作流内核。

用户已认可吸收 OhMyGame 的共用工具服务、可编辑产物契约、长任务恢复三项机制。来源与采用边界见 16，任务并入已有 W / E / C / S 对应阶段；不另建 Agent runtime、会话库或任务队列，也不将计划更新写成已实施。
