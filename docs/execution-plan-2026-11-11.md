## 3. 首期交付边界

使用一个脱敏软件产品夹具：两张导图、至少两个模块、一组既有设计文档；另备同工作区的第二产品检查隔离。不得直接拿生产库做破坏性验证。

首个流程为：冻结导图与约束 → 生成模块设计 → 提炼模块结构 → 生成产品设计 → 一致性报告。提供有人审和无人审两份固定模板：

- 有人审模板在各产出后插入 `human.edit-confirm`；可修改或直接确认原文，保存草稿不继续。
- 无人审模板在机器校验通过后系统采用并继续；同样需要输出完整、来源有效和权限满足。
- 一致性检查只交付报告；修复创建新尝试。人工意见与原始检查证据分开保存。
- 正式笔记和模块由声明的发布目标更新。有人审时绑定人工节点输出，不能在其上游自动采用时提前写回。
- 刷新、宿主重启、重复点击、迟到结果和旧入口修改均有明确恢复或冲突行为。

首期不纳入自由画布、多员工工作室、游戏工程、媒体生成、ComfyUI、向量检索和长期记忆。现有功能继续保留，扩展工作包不追加到 M1/M2 的完成条件。

## 8. 排期、责任与任务粒度

按单名主要开发者、可获得评审 / 产品验收支持安排；同一人可兼任角色，但技术完成和产品验收分别记录。建议只保持一个主开发批次进行中，每次变更可独立审查和停用。

| 角色 | 责任 |
| --- | --- |
| 产品 / 资料负责人 | 选试点、确认事实来源及有人审 / 无人审模板的业务结果 |
| Host / 数据实施者 | 状态、存储、工具隔离、恢复、发布和执行适配 |
| Client 实施者 | 最小入口、草稿编辑、冲突与来源展示 |
| 评审 / 验收者 | 对照阶段门检查测试、证据、兼容性和回退 |

M0 建议先给 **3–5 个工作日的探测时间盒**，这是待校准的投入建议，不是完成承诺。时间盒结束必须交付可用 / 不可用 / 未验证清单；未得结论的宿主项不阻断假执行器路线，也不能记为验证通过。

M0 结束后，再为 B1–B5 分别填写最可能 / 保守人日、负责人、评审人、验证与回退成本、置信度和阻塞项；不提前承诺全部平台的总工期。E02/K1 的配置和输入捕获、W1 的快照、W2 的页面等共享工作只估一次，真实后端特有适配另计。

每个实施变更应包含一项可观察行为及其必要验证，例如“重复确认只生效一次”“重启恢复人工待办”“报告不覆盖产品正文”；不要以“集成工作流平台”作为单个任务。

## 10. 主要风险与回退

| 风险 / 触发条件 | 处置 | 可用退路 |
| --- | --- | --- |
| 旧直写工具可绕过 staging | 阻止该执行配置接自动试点；验证工具集合和服务端身份校验 | M1 假执行器、人工导入候选 |
| 文档缺稳定身份或报告与正文撞键 | M0 定义显式产物 ID 和发布映射，添加多文档 / 跨图反例 | 保留原文，只导出候选，不发布 |
| blob / DB / outbox 故障导致内容不完整 | 对账已提交阶段，缺内容标 unavailable，禁止后继使用 | 在副本演练 DB + 对象库成组恢复 |
| 隐式记忆混入、必需输入截断 | 核查实际载荷；关闭未选内容注入；不足则停止自动派发 | 显式选取更小输入范围或人工导入 |
| 响应丢失后重复生成、取消不明 | 先持久化意图，保存 job/session，未知结果先对账 | outcome_unknown，不自动购买或发布 |
| 人工保存、系统采用被误作确认 | 独立 HumanTask、revision/CAS 与 actorType，发布绑定明确 | 保留草稿和快照，暂停相关运行 |
| 范围不断增加导致无法验收 | 先锁 M1/M2 出口；新能力归入原独立工作包 | 延后扩展，不降低核心验收条件 |
| 历史文档“已完成”被当作新环境通过 | 用当前源码、目标 profile 和实测证据逐项标状态 | 保留历史原结论，新结果另记日期 |

回退顺序：停止新领取 → 对账在途执行 → 关闭新入口 → 恢复旧入口并保留新历史只读。新增表、内容对象和用户文件保留；不以删表或清空目录完成回退。已经发布的笔记 / 工程只有当前 hash / revision 仍匹配发布基准时才能反向恢复，否则导出恢复副本供处理。

本次文档改动可通过只撤销新增索引、计划及导航提示回退；实施前已存在的 README/11/12/17 修改必须保留。计划完成后仍需经过 M0 探测，才能对实际开发量和真实接入能力作承诺。
