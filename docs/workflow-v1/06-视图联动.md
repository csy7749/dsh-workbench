# 工作流 v1 · 06 与任务视图联动

状态：设计已定，落在 M0.5 / M2 接线。回答「节点工作流能不能和行动清单、时间轴、看板、四象限联动」这个问题。

## 1. 先说清现状：四个视图本来就是同一份数据

它们不是四套数据，是同一份 `db.tasks⟫ 的四种投影，取数管线完全一样（`src/client/app.ts⟫）：

```text
pool()        :683    ui.scope==='all' ? db.tasks : 今天或进行中的
visible()     :699    matchQ && matchSpace && matchFilter && matchProject
                     ↓
  renderList     :1876  按 status 分 4 组：doing / next / waiting / done
  renderBoard    :1829  3 列：next / doing / waiting
  renderTimeline :1891  只要 date === todayKey()，按 start 排
  renderMatrix   :1911  按 priority + space 推断四个象限
```

四象限的判定是推断式的，没有显式字段（`app.ts:1913-1918⟫）：

| 象限 | 条件 |
| --- | --- |
| 重要且紧急 | `priority === 'high'⟫ |
| 重要不紧急 | `priority !== 'high' && space !== 'life'⟫ |
| 紧急不重要 | `priority !== 'high' && space === 'life'⟫ |
| 不重要不紧急 | `priority === 'low'⟫ |

**所以「互相看到数据」已经成立，不需要建同步机制。** 真正缺的是：工作流的人工节点不在这份数据里。

## 2. 接法：人工节点是虚拟任务，不是复制出来的任务

### 2.1 反例（不要这样做）

运行到人工节点 → 往 `db.tasks⟫ 插一条真任务 → 用户在看板勾完成 → 回调 `/confirm⟫。

问题：两个真相源。用户在任务里改了标题，草稿还是旧的；用户删了任务，运行永远卡在等确认；任务被导出再导入，变成幽灵任务。**任何「两边都能改」的设计最后都会分叉。**

### 2.2 正解

宿主（`src/workflow/m1-kernel.mjs⟫ 的人工待办）是唯一真相；客户端渲染时把它投影成任务对象并入 `pool()⟫：

| 字段 | 手工任务 | 工作流投影任务 |
| --- | --- | --- |
| `source⟫ | 缺省（视为 `manual⟫） | `'workflow'⟫ |
| `virtual⟫ | — | `true⟫（不可编辑字段、不进导出） |
| `runId⟫ / `nodeId⟫ / `graphId⟫ | — | 有 |
| 可改的 | 全部 | 只有「确认并继续 / 驳回 / 推迟」 |

投影是纯函数：`runs 摘要 → Task[]⟫，无副作用。**四个视图一行都不用改**，因为都走 `pool()⟫。

## 3. 四个视图各自怎么表现

| 视图 | 靠哪个字段进来 | 人工节点取什么值 | 点一下 |
| --- | --- | --- | --- |
| 行动清单 | `status⟫ | `'waiting'⟫（落进「等待中」组） | 打开该运行的草稿编辑 |
| 看板 | `status⟫ | `'waiting'⟫ 列 | 同上 |
| 时间轴 | `date⟫ + `start⟫ | 默认 `date=今天⟫、`start⟫ 取节点 config 的提醒时间；没设就不进时间轴 | 同上 |
| 四象限 | `priority⟫ + `space⟫ | `priority='high'⟫（等你确认＝马上要你做）、`space⟫ 取运行所属项目 | 同上 |

为什么四象限不改判定：改为显式 `quadrant⟫ 字段会影响所有既有任务的语义，v1 不动。用 `priority='high'⟫ 落到「重要且紧急」足够表达「流程卡在你这」。

## 4. 反向链接：任务 → 启动运行

| 位置 | 加什么 | 说明 |
| --- | --- | --- |
| `Task⟫ 接口 | `workflowRunId?⟫ / `workflowGraphId?⟫ | 这条任务派生出的运行 |
| 任务详情 | 一行「流程 3/6 步 · 等确认」 | 点进产品流程页对应运行 |
| 新建 / 编辑任务 | 「用流程执行」选模板 | 把这个任务当 `input.brief⟫ 启动 |

这样「我要做 X」和「X 怎么做的流程」是同一个对象的两个面，不用在两处各写一遍。

## 5. 第三个方向（v1 只留字段，不做）

`output.publish⟫ 的 `target⟫ 预留一项「生成待办」：流程跑完，把 `openQuestions⟫ / `acceptance⟫ 变成子任务。

理由：这是「流程产出工作」而不是「流程等待工作」，与人工节点方向相反，v1 不做但字段先占，避免以后改表。

## 6. 落地位置

| 层 | 文件 | 做什么 |
| --- | --- | --- |
| 客户端（纯函数） | 新增 `src/client/workflow/task-projection.ts⟫ | `projectRuns(runs): Task[]⟫，把待确认节点转成任务 |
| 客户端 | `src/client/app.ts:683⟫ `pool()⟫ | 合并投影任务（放在 `db.tasks⟫ 之后，用 `source⟧ 区分） |
| 宿主 | `GET /workbench-api/workflow/tasks?projectId=⟫ | 返回待办摘要（runId / nodeId / 标题 / 项目 / 截止 / 优先级） |
| 宿主 | M2 的 runs 列表 | 已有的运行摘要可以复用，不必新表 |

## 7. 必须处理的边界

| 边界 | 处理 |
| --- | --- |
| 导出 / 导入工作台数据 | 导出时**过滤掉** `source==='workflow'⟫，否则导出再导入会得到幽灵任务 |
| 计数（门户「已完成 N 项」、`projectTaskCount⟫ :797） | 统一在 `pool()⟫ 层过滤，否则数字虚高 |
| 运行结束 / 取消 | 投影任务自动消失（不是被勾掉） |
| 用户勾「完成」 | 只触发「确认并继续」，**不能**跳过节点；驳回走「驳回」按钮 |
| 时间轴只看今天 | 允许「推迟到明天」＝改节点提醒时间，不改运行状态 |
| 搜索 | `matchQ⟫ 里把运行名与节点标题拼进去，否则搜不到 |
